# ProvSci：TRUST 论文与结果数据智能体对照调研

> 日期：2026-08-18  
> 目的：解释聊天记录中的“过程数据/结果数据/可信度分层/verifier”，并转成 ProvSci 的可实现方案。

## 1. 先给结论

聊天里提到的两个链接，核心不是“结果数据智能体”的论文，而是**如何分层审核大模型推理过程**的工作：

1. `arXiv:2510.20188` 提出 TRUST 的第一版框架：把一条推理链拆成层级图，再把不同片段交给计算程序、LLM 或人类专家审核。
2. `arXiv:2604.27132` 是更完整的 TRUST 服务框架：在前一版的推理分解和多层审核基础上，又加入多智能体因果图、根因定位、局部修复、去中心化标注和治理。

聊天中的 **L0-Ln 不是这两篇论文里的标准术语**。学姐的想法应该是受到论文启发后，自己把“复杂度/可信度/人工审核成本”抽象成了一个层级路由问题。

更准确的说法应该是：

> **先把一句复杂结论拆成多个原子 claim，再根据每个 claim 的可验证性、难度和风险，选择最低成本但足够可靠的 verifier；只有自动方法不够时才升级到人类专家。**

这正好可以放进你的“结果数据智能体”里。

## 2. 两篇 TRUST 到底做了什么

### 2.1 TRUST 第一篇：审计一条推理链

- 标题：TRUST: A Decentralized Framework for Auditing Large Language Model Reasoning
- arXiv：<https://arxiv.org/abs/2510.20188>
- 提交时间：2025-10-23
- 核心问题：一条很长的推理链，不能每次都让人从头到尾检查，也不能只看最终答案。

#### 它的基本流程

```text
模型生成推理链
    ↓
按语义层级拆成 HDAG
    ↓
每个节点判断难度和类型
    ↓
计算程序 / LLM / 人类专家分别审核
    ↓
按节点、片段、整条轨迹聚合结果
```

这里的 **HDAG（Hierarchical Directed Acyclic Graph，层级有向无环图）**，可以理解成把一条线性的思维过程改造成一张有父子关系的检查清单。

它定义了五种推理抽象层级：

| 层级 | 中文理解 | 例子 |
|---|---|---|
| Goal | 要完成什么 | 求论文中某药物的 IC50 |
| Strategy | 总体怎么做 | 从 Table 2 提取数值并统一单位 |
| Tactic | 具体采用什么方法 | 选择 Compound 7 的 IC50 列 |
| Step | 一步逻辑动作 | 读取该行数值并判断单位 |
| Operation | 原子操作/计算 | `12.5 μM → 1.25e-5 M` |

论文明确提出的五层是“推理结构层级”，不是可信度等级。citeturn22view0

#### 审核者怎么分

TRUST 的审核者主要分成三类：

| 审核者 | 负责什么 | 典型例子 |
|---|---|---|
| Computer | 确定性检查 | 算术、单位换算、代码执行、格式、API 返回值 |
| LLM | 语义和普通逻辑 | 证据是否支持结论、步骤是否连贯、是否漏条件 |
| Human | 高歧义、高风险判断 | 医学/法律结论、复杂策略、自动审核争议 |

论文中的路由依据包括：节点所在层级、难度、领域和错误后果。它给出的示例分配是：Operation 多交给计算程序，简单/中等 Step 交给 LLM，困难的 Step、Strategy 和 Goal 才升级到人。citeturn27view4

#### 论文实验告诉我们的事

论文在一个 200 题、四领域的推理审核实验中报告了：TRUST 在无污染设置下准确率 72.4%，高于单个审核模型和普通投票；在 20% 审核者被人为污染时，准确率仍为 63.4%。在一个很小的 10 道数学题、15 名博士生参与的人类实验中，HDAG 版本 F1 为 0.89，Brier score 为 0.074；随机切分或固定长度切分的版本 F1 只有 0.40。citeturn25view1 citeturn26view0

这些数字只能说明“结构化分层有潜力”，不能直接理解成一个已经被大规模验证的工业系统。实验规模、任务类型和审核者质量都有限，而且论文自己也承认 HDAG 分解会带来延迟，LLM 审核者也会继承模型偏差。citeturn26view0

### 2.2 TRUST 第二篇：从推理审核扩展到多智能体服务

- 标题：TRUST: A Framework for Decentralized AI Service v.0.1
- arXiv：<https://arxiv.org/abs/2604.27132>
- 提交时间：2026-04-29
- 论文性质：arXiv v1 框架/白皮书式工作，不能直接当成已经成熟部署的产品证明。

第二篇保留了第一篇的 HDAG 和三类审核者，又加了三件对你们更有用的东西：

#### 1. CIG：追踪多智能体之间的因果传递

**CIG（Causal Interaction Graph，因果交互图）**不是只记录“谁调用了谁”，而是记录：

- 哪个智能体发了什么输入；
- 下一个智能体收到后输出了什么；
- 信息有没有在传递中丢失、变形或被错误理解；
- 最终错误应该归到哪个上游节点。

这解决的是“最后一个智能体看起来答错了，但真正的错误其实来自更早的输入”的问题。第二篇把错误分成：

- `Invalid_Root`：真正的根错误；
- `Invalid_Cascade`：被上游错误污染的连带错误；
- `Negligent`：审核者明明应该发现错误却放过了；
- `Valid`：通过审核。

#### 2. 局部修复，而不是整条链重做

第二篇提出 `Prune-Freeze-Repair`：

1. 找到根错误节点；
2. 删除该节点和受污染的下游节点；
3. 保留不依赖错误节点的正确结果；
4. 只重新生成出错子图；
5. 再次审核。

这就是聊天里“减轻人工验证 burden”的关键工程思想：不是每次发现一个小错误都把整个任务推倒重来。

#### 3. 三层审核不等于三种“真理等级”

第二篇给出的三层审核成本/延迟大致是：

| 级别 | 方式 | 适合任务 | 论文给出的典型占比 |
|---|---|---|---:|
| Tier 1 | 计算程序 | 算术、单位、代码、格式 | 60–70% |
| Tier 2 | LLM 审核 | 语义、普通逻辑、证据支持 | 25–35% |
| Tier 3 | 人类专家 | 高歧义、高风险、争议 | 5–10% |

论文把这看成成本和可靠性之间的路由，而不是“Tier 3 一定正确”。它自己也明确写到，LLM 有偏差，人类也有疲劳和专业差异，因此需要多审核者和质量校准。citeturn27view4

## 3. 学姐说的 L0-Ln 应该怎么理解

### 3.1 她实际想表达的东西

聊天里的意思大概是：

> 一句话结论太复杂，人类直接判断很贵；先让系统把它拆成更小的 claim，每个 claim 分别判断。简单的可以程序验证，中等的让 LLM 验证，真正困难的才找专家。

这不是给“答案”打一个简单的 0–100 分，而是给**审核任务分配合适的审核方式**。

### 3.2 不建议直接叫 L0-Ln

因为你们项目里至少存在三种不同的“层级”，混在一起会很乱：

1. **推理结构层级**：Goal/Strategy/Tactic/Step/Operation；
2. **验证审核层级**：Computer/LLM/Human；
3. **结论可信度分数**：比如 0.82、0.94。

建议工程里用三套不同字段：

```text
abstraction_level: goal | strategy | tactic | step | operation
verification_tier: deterministic | llm | expert
confidence: 0.0 - 1.0
```

**confidence 不能代替 verification。** 一个 LLM 说“我有 95% 把握”，并不等于这个结论真的经过验证。

### 3.3 推荐的项目版审核等级

你可以先不用区块链，直接实现下面这套本地路由：

| 项目级别 | 触发条件 | 审核方式 | 是否进入 Gold |
|---|---|---|---|
| A0 可计算 | 数字、单位、格式、代码可确定执行 | Python/SymPy/Pint/规则 | 通过即可 |
| A1 可语义判断 | 证据支持、简单分类、非歧义关系 | 一个独立 LLM verifier | 需达到阈值 |
| A2 需交叉核验 | 多句组合、条件复杂、模型间有分歧 | 多 LLM/检索/反向问题/重复抽取 | 需一致或人工复核 |
| A3 专家判断 | 因果解释、领域争议、高风险结论 | 领域专家 | 专家确认后进入 Gold |

这比“L0 最不可信、Ln 最可信”更准确，因为它描述的是**验证成本和验证能力**，不是直接声称某一层的真理性。

## 4. 这和你的“结果数据智能体”怎么接

### 4.1 过程数据智能体和结果数据智能体的区别

| 维度 | 过程数据智能体 | 结果数据智能体（你） |
|---|---|---|
| 关注对象 | 智能体怎么想、怎么规划、怎么调用工具 | 论文/实验里最终产生了什么数据和结论 |
| 主要输入 | 任务、观察、工具返回、消息、历史状态 | PDF、表格、图、补充材料、实验结果 |
| 主要输出 | trajectory、步骤、工具轨迹、错误恢复记录 | 结构化结果、标签、单位、证据、数据卡 |
| 核心问题 | 过程是否合理、是否跑偏、哪里出错 | 数据是否抽对、处理对、分类对、证据是否支持 |
| 典型评测 | 任务成功率、恢复率、工具调用正确率 | 抽取准确率、单位准确率、标签 F1、证据精度、复算率 |

两者确实都需要推理，但“推理的对象”不同：

- 过程智能体推理的是“下一步怎么做”；
- 结果智能体推理的是“这条数据是什么、怎么处理、能不能相信”。

### 4.2 你的结果数据智能体应该长什么样

你不只是做一个固定的 PDF 抽取脚本，而是做一个带有动态决策和验证的混合系统：

```text
论文/实验结果
    ↓
结果候选发现
    ↓
原子 Claim 拆分
    ↓
证据定位与数据抽取
    ↓
单位归一化 / 数值计算 / 分类标注
    ↓
验证等级路由
    ├─ A0：程序直接复算
    ├─ A1：LLM 检查语义与证据
    ├─ A2：多模型/多来源交叉核验
    └─ A3：人类专家复核
    ↓
结构化结果数据卡 + 审核日志
```

### 4.3 一个具体例子

假设论文中有一句：

> 某化合物在 10 μM 浓度下使细胞活性下降 30%，提示其可能诱导凋亡。

不要把它当成一句整体结论，而要拆成：

| Claim | 内容 | 推荐审核 |
|---|---|---|
| C1 | 化合物名称和实验组 | A0：表格行列定位 |
| C2 | 浓度为 10 μM | A0：数值和单位检查 |
| C3 | 细胞活性下降 30% | A0：表格/图读数 + 算术复算 |
| C4 | 下降发生在该条件下 | A1：证据与条件语义检查 |
| C5 | “提示诱导凋亡” | A2/A3：因果强度和领域解释检查 |

如果 C3 的数值抽错了，C5 就不能继续被当作可信结论；它应标记成 `Invalid_Cascade`，而不是单独再让一个 LLM 给它打高分。

## 5. “workflow 过时了吗？”

不建议这么理解。

**Workflow** 负责把关键步骤固定下来，优点是稳定、可复现、容易测试；**Agent** 负责在遇到不同文献、不同表格和失败情况时动态决定下一步。

你们真正适合做的是：

> **固定的验证骨架 + Agent 化的任务规划和异常处理。**

例如：

- “单位转换必须走 Pint”是 workflow 规则；
- “这篇论文没有标准表格，改用 OCR 还是转向补充材料”是 agent 决策；
- “算术结果必须由程序重跑”是 workflow 规则；
- “LLM 和表格抽取器结果冲突，是否升级专家”是 agent 决策。

完全自由发挥的 Agent 反而不适合做科学数据生产，因为它会让每条数据的处理过程不一致，最后无法复现。

## 6. 你具体应该负责哪些工作

### 第一层：定义“结果数据是什么”

- 结果类型：数值、表格项、比较关系、分类、机制结论；
- 必填字段：值、单位、条件、对象、时间点、对照组；
- 证据字段：页码、表号、行列、图号、原文片段；
- 失败类型：OCR 错误、单位歧义、条件缺失、证据不足、因果过度解读。

### 第二层：做结果处理工具

- 表格单元格抽取；
- 数字和单位解析；
- 单位统一；
- 算术和统计量复算；
- 分类和标签标准化；
- 结果去重和冲突合并。

### 第三层：做验证路由

- 哪些结果可以程序自动过；
- 哪些结果需要 LLM 进行证据一致性判断；
- 哪些结果必须交叉检索或多模型复核；
- 哪些结果必须升级给专家。

### 第四层：做结果数据评测

- 数值抽取准确率；
- 单位准确率；
- 标签 F1；
- 证据精度；
- 路径复现率；
- 自动通过样本的专家抽检错误率；
- 人工审核时间节省比例。

## 7. 和已有工作的关系

这两篇 TRUST 不是孤立的。你们要借鉴的研究脉络至少有四条：

1. **Process supervision**：不是只看最终答案，而是监督中间步骤。Google 的 MiPS 工作用模型采样中间步骤的后续正确率，自动构造过程监督数据，目标就是减少人工逐步标注成本。citeturn31view0
2. **Graph-based verification**：Graph of Verification 用图结构和可变粒度做验证，允许正式计算题按原子步骤检查，自然语言任务按段落检查。citeturn30view0
3. **TRUST / HDAG**：把推理结构分层，并根据难度把节点路由给程序、LLM 或专家。citeturn27view4
4. **CIG / active repair**：追踪多智能体之间的输入输出和错误传播，只修根错误及其下游。citeturn24view2 citeturn24view3

因此，你们的论文不能只写“我们做了一个数据处理 Agent”，这个说法太像工程系统。更有研究味道的表述是：

> **A claim-level, provenance-aware result data agent with adaptive multi-tier verification.**

中文可以说：

> **一个面向科学结果数据的、带证据溯源和自适应多级验证的智能体。**

## 8. 建议的第一版研究问题

### RQ1：原子 Claim 拆分是否能提高结果数据审核效率？

比较整句审核、固定长度切分和基于语义/依赖关系的 Claim 图切分。

### RQ2：自适应验证路由能否在不显著降低准确率的情况下减少专家审核？

比较：全部人工、全部 LLM、全部统一 verifier、A0/A1/A2/A3 自适应路由。

### RQ3：依赖关系感知的错误传播和局部修复是否比整条结果链重跑更省成本？

比较全量重做和只修复根错误及其下游节点。

## 9. 最小可行实现顺序

不要一上来实现论文里的区块链、代币、去中心化网络。先做最有研究价值、也最容易验证的核心：

1. 选一个垂直域，例如 IC50/EC50/浓度数据；
2. 定义 ResultRecord 和 ClaimNode schema；
3. 做表格/文本抽取；
4. 做 A0 确定性 verifier；
5. 做 A1 LLM evidence verifier；
6. 做 A2 分歧升级；
7. 建 100 条人工金牌测试集；
8. 比较“整句审核 vs Claim 图 + 多级路由”；
9. 记录准确率、专家调用率、成本和延迟。

这样就已经足够形成一篇早期论文或技术报告的实验骨架。

## 10. 最后用一句话理解学姐的意思

她不是让你做一个“会自己想的聊天机器人”，而是让你做一个**会把科学结果拆开、处理、标注、追溯，并且知道什么时候该相信程序、什么时候该问 LLM、什么时候必须找专家的数据智能体**。
