# ProvSci 老师演示方案 v1

这是一套面向 8–10 分钟现场展示的“效果检验 + 可审计性”演示。主线使用真实开放论文 `PMC8415024`，备用展示使用同一批处理中的 4 篇真实 PMC/JATS 论文。所有数字均来自本地可重跑产物，不把自动生成的数量误报成人工准确率。

## 一句话定位

ProvSci 输出的不是一段看起来合理的回答，而是一条带来源、证据、条件、单位、处理路径、验证状态和质量等级的结构化结果记录。老师可以从结果卡一路回看到原文表格，并让 verifier 重新计算答案。

## 技术原理讲解稿（通俗版）

可以先用一句话定调：**这个智能体像一条科研数据质检流水线，不是一个只会生成文字的聊天机器人。** 它先从论文里找出可能的结果，再把结果的出处和处理步骤记下来，最后由 verifier 像第二个质检员一样重新验货。只有“数字、条件、原文位置和重算结果”全部对得上，才会标成 Gold。

### 一次处理的 8 个步骤

1. **读取原始文件。** 输入可以是 PMC/JATS XML 或 JSON。系统保留原文件、文献编号、许可证、来源 URL、下载时间和 SHA-256 hash。hash 可以理解为文件指纹，确保以后复核的还是同一份论文。
2. **格式适配。** 不同论文的 XML 标签可能不同，适配器先把正文、章节、表格和图注整理成统一结构，并保留表格 ID、行名和列名。系统先整理材料，再开始找答案。
3. **挖掘候选。** miner 在结果相关章节和表格中寻找数字、单位、实体和条件。例如从 `15.34 ± 0.81 μM` 识别出数值 15.34、误差 0.81 和单位 μM，同时识别 SW480、IC50、24 h。此时只是“可能的答案”。
4. **生成 ResultCard。** 候选被装进固定字段：`entity`、`metric`、`value`、`uncertainty`、`unit`、`condition`、`source`、`evidence` 和 `acquisition_path`。固定字段让不同论文的结果可以比较，也让程序能逐项检查。
5. **生成 evidence locator。** 系统保存原文片段和精确位置，例如 `TABLE 1 → row SW480 → col IC50(μM) / 24 h`。因此演示时可以从一个数字直接回到论文中的那一个单元格。
6. **记录 acquisition path。** 路径是“这个数是怎么得到的”操作清单，例如 `extract_table_cell → parse_measurement`。每一步都有输入、参数和输出，别人可以照着重做，而不是只能相信最终字符串。
7. **verifier replay。** verifier 会暂时把候选答案清空，沿着同一条路径重新读取原文、解析均值和误差，再比较数值、单位、条件、证据片段是否一致。通过后才写入 `verification.status=pass`。
8. **质量分流。** 全部门禁通过的是 Gold；找到了数字但条件或许可不完整的是 Silver；主客体不清、证据冲突或路径不能复现的进入 Human Review。系统保留证据，不把不确定性伪装成确定答案。

### API 是怎样接入的

现场可以把 API 分成三层解释：

- **论文来源 API：负责“拿资料”。** `fetch-pmc` 请求 Europe PMC 的 `fullTextXML` 接口，例如 `GET https://www.ebi.ac.uk/europepmc/webservices/rest/PMC8415024/fullTextXML`，下载后写入本地，并记录来源元数据和 hash。
- **智能体 Python API：负责“加工资料”。** `ScientificDataAgent.run(input_path, output_dir)` 触发完整流水线：读取、适配、挖掘、生成 ResultCard、证据和 path、运行 verifier，并写出 `all.jsonl`、`summary.json` 等产物。
- **查询 API：负责“找已验证结论”。** `ScientificDataAgent.ask(question, results_dir)` 读取已有结果，只筛选 `verification.status=pass` 的样本，再做透明的关键词匹配，返回答案、证据、处理路径和验证轨迹。

可以展示这段最小调用：

```python
from provsci.agent import ScientificDataAgent

agent = ScientificDataAgent()
agent.run("paper.nxml", "work/run")
answer = agent.ask(
    "What IC50 was reported for SW480 under 24 h?",
    "work/run",
)
```

命令行只是这两个 Python 方法的外壳：CLI 把 `--input`、`--output`、`--question` 等参数转换成函数参数，再把返回对象写成 JSON/JSONL。当前核心是本地 Python API，不是已经部署在服务器上的 HTTP 服务；`review-serve` 只负责把人工复核页面提供给浏览器。

### 为什么现在没有直接调用大模型

当前演示先用规则、结构化解析和确定性 verifier 把“证据—路径—验证”闭环固定下来，因此运行成本基线为 $0，也便于老师逐步复核。未来大模型可以放在候选挖掘或问题理解的位置，帮助判断实体、指标和条件，但输出仍必须进入 ResultCard，并经过 evidence locator、acquisition path 和 verifier replay；模型可以找线索，不能直接盖 Gold 章。

### 一句收束

> 这套系统的核心不是“回答得像不像人”，而是“每个答案能不能回到原文、能不能按记录重算、不能确定时能不能明确交给人”。

## 演示前准备

如果要展示“产品形态”而不只是验证驾驶舱，优先打开：

```text
web/product_workspace.html
```

这个工作台采用了公开文献分析产品常见的工作区布局：左侧运行导航，中间文件投递和结果表格，右侧显示当前行的证据、处理路径和 verifier 状态。点击“载入演示论文”可以直接进入真实数据演示；也可以拖入 JSON/CSV/TXT 文件预览浏览器端解析结果，再点击“开始分析”查看五个处理阶段。当前上传解析是前端原型，完整的 ProvSci 后端调用仍通过本地 Python pipeline 运行。

在项目根目录运行：

```bash
sh scripts/run_teacher_demo.sh work/teacher-demo-v2
```

脚本会调用当前 P0 闭环，随后生成自然语言查询结果和静态人工复核工作台。默认不会联网，也不会调用模型；论文 fixture 已放在 `examples/real/`，因此现场网络不稳定时仍可运行。

准备完成后，重点文件如下：

| 用途 | 文件 |
|---|---|
| 主论文原文（可打开看 Table 1） | `examples/real/PMC8415024.nxml` |
| 四篇真实论文批处理摘要 | `work/teacher-demo-v2/p0/real-smoke/summary.json` |
| 四篇论文结果卡（含主论文） | `work/teacher-demo-v2/p0/real-smoke/result_cards.jsonl` |
| 可视化驾驶舱（推荐首屏） | `work/teacher-demo-v2/teacher_dashboard.html` |

| 查询结果精简预览 | `work/teacher-demo-v2/p0/real-smoke/query_sw480_ic50_preview.json` |

如果需要展示交互式复核，可在本机启动回环地址服务：

```bash
PYTHONPATH=src python3 -m provsci.cli review-serve \

  --host 127.0.0.1 --port 8765
```

浏览器打开 `http://127.0.0.1:8765/`。不需要交互时，直接打开静态 HTML 即可。

## 8–10 分钟逐分钟脚本

### 可视化首屏（推荐）

现场优先打开 `work/teacher-demo-v2/teacher_dashboard.html`。左侧是论文与演示导航，中间是 `SW480`/`SW1116` 的 IC50 时间曲线，右侧同步显示当前点的证据 locator、acquisition path 和质量门禁。点击曲线上的点或 `12 h / 24 h / 36 h` 按钮，老师可以直接看到“同一篇论文的不同条件如何成为不同结果样本”。

### 0:00–0:45：先讲问题和边界

可以这样说：

> 我们现在验证的不是“模型能不能总结一篇论文”，而是能不能把论文里的定量结果生产成可复核的数据样本。每个样本都要有结果卡、原文证据、条件和可执行路径；缺少关键语义的候选不会被硬塞进 Gold，而是进入 Silver 或 Human Review。

强调当前是通用 `scientific_quantitative_result_v1` 场景，示例论文来自生物医学只是为了有清晰的表格和 IC50 数值，不代表产品只做这个领域。

### 0:45–2:00：给出真实输入

打开 `examples/real/PMC8415024.nxml`，定位 `TABLE 1`。指出：

- 行标签包含 `SW480`；
- 列包含 `IC50(μM) / 24 h`；
- 单元格是 `15.34 ± 0.81`；
- 这同时提供了实体、指标、数值、误差、单位和条件。

如果不想在 XML 中现场查找，可以展示脚本生成的 `result_cards.jsonl`，再回到相同的 `TABLE 1` locator。

### 2:00–3:30：运行抽取并看规模

```bash
PYTHONPATH=src python3 -m provsci.cli batch \
  --manifest examples/benchmark/real-smoke-manifest.json \
  --output work/teacher-demo-v2/p0/real-smoke \
  --strategy result_focused
```

展示 `summary.json` 中的四篇结果：192 个候选、186 个 Gold、6 个 Silver/Human Review、Evidence Coverage 1.0、Path Reproducibility 1.0。说明这里是 smoke，主要检验稳定性和审计不变量；严格语义分数看下一步的人工 manifest。

### 3:30–5:00：展开一张 ResultCard

从 `result_cards.jsonl` 找到 `PMC8415024`、`SW480`、`IC50`、`24 h` 的样本，展示以下字段：

```text
entity: SW480
metric: IC50
value ± uncertainty: 15.34 ± 0.81
unit: μM
condition: 24 h（column_header，explicit）
result_type: measurement
quality: Gold / verification.status=pass
```

接着展示 evidence locator：`TABLE 1 → row SW480 → col IC50(μM) / 24 h`，以及原始单元格文本 `15.34 ± 0.81`。强调 `result_cards.csv` 只是分析平面视图，审计时应打开 JSONL。

### 5:00–6:15：展示 acquisition path 和 verifier trace

展示路径的两个步骤：

```text
extract_table_cell
→ parse_measurement
→ verifier replay
```

解释：第一步从指定表格行列取出原始字符串，第二步解析数值、误差和单位；verifier 清空答案后沿同一路径重算，得到 `15.34 μM` 和 `0.81` 误差，且证据片段与 locator 一致，所以状态为 `pass`。这一步是产品和普通摘要问答的差异点。

### 6:15–7:15：执行一次自然语言查询

```bash
PYTHONPATH=src python3 -m provsci.cli ask \
  --results work/teacher-demo-v2/p0/real-smoke \
  --question "What IC50 was reported for SW480 under 24 h?" \
  --limit 3
```

也可以直接打开 `query_sw480_ic50_preview.json`。预期答案为 `15.34 ± 0.81 μM`，条件为 `24 h`，并同时返回 evidence、path 和 verification trace。说明 `ask` 只检索已通过 verifier 的结果，不绕过质量门禁；当前查询排序是透明词法基线，后续可替换检索/LLM 排序器。

### 7:15–8:15：故意展示一个需要人的样本

打开 `review_workbench.html`，选择 `underspecified_relation` 样本。指出：系统确实找到了正文中的比较关系，但主语可能以 “As shown/To determine/when” 开头，无法稳定确定主客体；因此保留完整证据和 provenance，却不把它冒充为 Gold。

可补充说明：`human_review.jsonl` 是正式产物，人工可以 `accept/modify/reject`，决策以追加日志保存，不覆盖原始候选。

### 8:15–9:15：给出严格 benchmark

打开 `work/teacher-demo-v2/p0/benchmark/evaluation.json` 的 `result_focused` 部分，口头报：

| 指标 | 当前 P0 结果 |
|---|---:|
| 文献数 | 2 篇真实 CC-BY PMC/JATS |
| 人工核验 claim | 52 条 |
| Claim Recall / Precision | 1.0000 / 1.0000 |
| Evidence locator Precision / Recall | 1.0000 / 1.0000 |
| Condition match rate | 1.0000 |
| Path Reproducibility / Evidence Coverage | 1.0000 / 1.0000 |
| 运行成本基线 | $0（纯本地确定性，无模型调用） |

立刻补上限定语：这是小规模、固定 manifest 的人工 benchmark，不能外推成跨领域总体准确率。另可展示 `table_only` 与 `full` 对照：前者召回低，后者召回高但 precision 只有 0.3152，说明 section-aware 路由和语义门禁确实有作用。

### 9:15–10:00：收束和下一步

建议收束为：

> 今天验证的是一个可运行的可信闭环：真实论文 → 结构化结果 → 原文定位 → 可执行路径 → 确定性复算 → Gold/Silver/Human Review。下一步不是继续堆更多“看起来像答案”的文本，而是扩大人工 Gold、接入复杂 PDF/图表解析，并在确定领域 schema 后做更大规模评测。

## 老师可能追问

**“这是大模型结果吗？”**  当前演示默认是规则和确定性处理，没有模型调用，目的是先把证据、路径和验证契约冻结。模型可以用于候选生成或语义排序，但不能绕过 verifier。

**“为什么有些抽到了却不是 Gold？”**  Gold 不只检查数字，还检查实体、指标、单位、条件、证据和许可。关系主客体不稳定、许可证未知或跨证据冲突时，样本进入 Silver/Human Review。

**“1.0 是不是代表系统已经达到 100%？”**  不是。1.0 只表示在这 2 篇、52 条人工 claim 的固定 P0 manifest 上完全匹配；样本规模和文档类型都有限。

**“为什么不用全量抽取？”**  `full` 作为高召回对照会混入方法描述、剂量序列和条件噪声，P0 precision 为 0.3152。默认 `result_focused` 先保证结果语义和可复核性。

**“能不能改错结果？”**  可以人工 `modify`，但修改后会重新 replay；答案、证据或 path 被篡改会触发 `answer_mismatch`、`evidence_mismatch` 等失败，不会静默进入 Gold。

**“能处理图吗？”**  当前 multimodal 通道支持 JATS 图注 alt-text 和显式结构化曲线点；像素级 OCR/VLM 读图仍是后续适配器工作，现场不要把它描述成已解决的通用图表识别。

## 现场验收清单

- [ ] 能从主论文定位到 `TABLE 1 / SW480 / IC50(μM) / 24 h`。
- [ ] 能展示 `15.34 ± 0.81 μM` 及其 condition/evidence。
- [ ] 能展示 `extract_table_cell → parse_measurement → verifier replay`。
- [ ] 能执行 `ask` 并返回同一结果及 trace。
- [ ] 能展示至少一个 `underspecified_relation` 人工复核样本。
- [ ] 能报出四篇 smoke 的规模和 P0 人工 benchmark 的限定语。
- [ ] 不把 Silver/Human Review 说成错误被删除，也不把自动 Gold 说成人工标注。

## 备份方案

如果现场浏览器或批处理出现问题，直接打开脚本已生成的静态文件：

1. `query_sw480_ic50_preview.json`：最短成功路径；
2. `result_cards.jsonl`：完整结果卡和证据；
3. `review_workbench.html`：人工复核页面；
4. `benchmark/evaluation.json`：严格指标。

若只剩 2 分钟，依次展示查询预览、evidence locator、path/verification trace 和一个人工复核样本即可；这四项比单独报候选数量更能说明产品效果。
